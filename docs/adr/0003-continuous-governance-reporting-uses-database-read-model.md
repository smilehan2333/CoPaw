# Continuous Governance Reporting Uses a Database Read Model

Management-side Continuous Governance Analysis and statistics will read from a database-backed reporting model rather than scanning workspace files at request time. This applies to governance records, coverage, governed-user counts, success and outcome metrics, trends, distributions, file-governance state reports, cleanup audits, archive state, protected files, and purge metrics. Workspace files remain the execution and immediate-operation source for current workspace actions, but management reporting uses the database model to keep source-scope analytics consistent across users, workspaces, and instances. The read model is written or updated at governance execution and file-governance action boundaries: dream optimization creates governance records and execution impact, rollback updates the original record outcome, archive/restore/protect/purge updates file-governance state, and audited administrator batches write cleanup audit. During the compatibility period, execution paths dual-write workspace files and the database read model; management-side statistics still treat the database model as authoritative and must not fall back to request-time workspace scanning. A management-visible governance or file-governance action is successful only after the database read model reflects the action; if workspace file changes succeed but the database write fails, the action must not be reported as management-side success until retry, compensation, or an explicit pending/failure state resolves it. Analysis queries only read the database model; they do not scan workspace files, repair records, or backfill missing state as a side effect. Existing workspace files such as dream logs, archive indexes, protected-path state, and audit logs will be imported by an explicit idempotent migration or backfill task triggered by an administrator or deployment process. After that migration, workspace files may remain for current-workspace operation compatibility, but management-side statistics treat the database model as authoritative. Database reporting identities are source-scoped domain identities: source id, logical managed user id, and workspace or agent id. Runtime tenant directory names are technical file-location mappings and must not become the reporting primary key.

If a dual-write operation changes workspace files but cannot update the database read model, the recovery model is pending plus retry or reconcile rather than immediately rolling back workspace files. File movement, deletion, and archive state changes may be costly or unsafe to reverse synchronously; the action remains non-successful for management reporting until a retry, reconciliation job, or administrator-visible failure state resolves the database model.

Management-side analysis metrics only aggregate committed successful database read-model rows. Pending, failed, or reconcile-needed rows are exposed separately as health state or exception lists so administrators can repair them without mixing partial actions into core coverage, success, archive, protected-file, or purge metrics.
